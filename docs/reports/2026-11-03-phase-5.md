## Investigation (as asked before implementing; plan approved in Phase 0 with decision D7)
| Question | Finding |
|---|---|
| Where is the previous state after the ping-pong? | Right after `step()` it is the other target, `targets[1 - read]` (`src/simulation/lenia.js`); exposed as the read-only getter `previousTexture`. The next step overwrites it |
| Steps per frame | Up to `LOOP.maxStepsPerFrame` = 4; 1 while GPU-limited |
| Per step or per frame? | Per step (D7): only the last step's previous state survives a frame, and per-frame decay would depend on the frame rate |
| Memory | Two extra textures of grid^2 values in the state format: 128 KiB at grid 128, 2 MiB at 512 (float32); allocated only while an aid is on |
| Extra passes | One accumulation pass per step (2 to 3 texel reads per cell), none when off; the display pass is unchanged in count |
| Format | The state's probed renderable format (R32F, or R16F as fallback) |
| Context restore | Dropped on loss without GL calls (like the readback), recreated by `initGpu()` if a mode is on, starting cleared |
| Cost at 128 and 512 | Measured by GPU timer query (below) |

## What changed
- `src/shaders/overlay-accumulate.frag.js` (new): trails `H' = max(H * decay, A)`; activity `H' = H * decay + |A - A_prev|`.
- `src/gl/overlay.js` (new): `OverlayAccumulator` (own ping-pong pair; `accumulate`, `clear`, `readValues` for tests,
  `dispose`) and `OVERLAY_MODE`.
- `src/simulation/lenia.js`: the read-only getter `previousTexture` only. The step shader, kernel and equations are unchanged.
- `src/shaders/display.frag.js`: `uOverlay`, `uOverlayMode`, `uOverlayScale`; with the mode 0 the state path is the same
  expressions as before (the default-view byte-identity check still passes).
- `src/render/renderer.js`: `draw(..., overlay = null)`.
- `src/app.js`: `visualMode` ('off' default), `decay`, `overlay`; `setVisualMode`, `setDecay` (finite, limited to
  [0.80, 0.999]); one accumulation after each step in `submitFrame`; cleared by `reset()` (so by Reset, a switch and a
  placement); dropped on loss and recreated in `initGpu()`; falls back to off with a note if allocation fails.
- `src/ui/controls.js`, `index.html`: an Overlay row (Off / Trails / Activity), a "Fade per step" slider with the half-life in
  steps, and a sentence saying what the aid shows, that it is derived from the state and display only.
- `src/ui/tour.js`: the tour turns the aid off when it opens (it describes the state itself).
- `src/config.js`: `VISUAL` (modes; decay 0.80 to 0.999, step 0.001, default 0.95). LIMITS unchanged.
- Tests: `gpu-parity.js` (4 checks and 2 cost info lines), `ui-flow.js` (14 checks), `shaders.test.js` (new shader),
  `ui-config.test.js` (1 test).
- Docs: `DECISIONS.md` 30, `README.md`, `progress.md`.

## Cost (D7: measured, Reported)
GPU timer query (`EXT_disjoint_timer_query_webgl2`) in `gpu-parity.html`, informational, not asserted, one run:

| Grid | Step pass | Accumulation pass | Ratio |
|---|---|---|---|
| 128 (20 passes each) | 0.752 ms | 0.008 ms | 1.07 % |
| 512 (4 passes each) | 10.086 ms | 0.072 ms | 0.71 % |

The Phase 0 estimate ("under 1 %") was slightly low at grid 128. Frame-rate effect in an ordinary browser: Unverified (the
built-in pane throttles frames). The timer resolution and the effect of the pane's throttling on these GPU times are not known.

## Notes and risks
- With the default fade the activity map is dim (in one probe its brightest value was 0.16 of the scale), because it is scaled
  to the largest possible change rather than to what the organism does. That is the honest scale; a brighter scale would need a
  stated, different normalization (owner decision).
- Both aids share the selected colour map; a separate map for activity is listed under Planned.
- `lenia.js` gained a getter (not a change to the simulation), as `stateFramebuffer` did for the Observatory.
