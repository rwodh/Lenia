## GPU-limited flag (item 3): measurement and proposal
Scratchpad probe in the live page (timer query `EXT_disjoint_timer_query_webgl2` around each submitted frame; fence latency
counted in animation frames), 15 s per run, playing at 60 steps/s. Reported.

| Grid | GPU ms per frame p50 / p90 | Frame interval p50 | Fence frames to signal p50 / p90 | Frames held back | Flag on | Steps/s |
|---|---|---|---|---|---|---|
| 64 | 0.88 / 1.73 | 7.0 ms (144 Hz) | 2 / 2 | 57 % | 73 % | 55 |
| 128, run 1 | 1.05 / 2.42 | 7.0 ms | 1 / 2 | 40 % | 23 % | 62 |
| 128, run 2 | 0.97 / 2.59 | 7.0 ms | 1 / 2 | 43 % | 53 % | 55 |
| 128, run 3 | 1.03 / 3.29 | 7.0 ms | 2 / 2 | 64 % | 95 % | 52 |
| 256 | 1.84 / 9.00 | 7.0 ms | 2 / 3 | 64 % | 100 % | 49 |

At grids 64 and 128 the GPU is busy about 1 ms of each 7 ms frame, but a fence signals after 1 to 2 frames: presentation
latency, not load. With `LOOP.maxFramesInFlight` = 2 the loop holds back 40 to 64 % of frames, so the flag is on most of the time,
the simulation runs below 60 steps/s, and the Observatory stops sampling. **So the flag is mostly a false positive on this
144 Hz display.**

Proposal (not implemented; it changes the in-flight cap that `FrameFence` enforces, so it needs the owner's decision):
1. Raise `LOOP.maxFramesInFlight` from 2 to 3 (config only; `FrameFence` code unchanged). At 144 Hz that allows about 21 ms of
   queued work, still a bound. Re-measure the same table; acceptance: flag below 10 % and 60 steps/s at grid 128 on this machine.
2. Alternatively, keep the cap and set the flag only when frames are held back for several frames in a row (app.js only). This
   would fix the flag and sampling but not the lost steps, because held-back frames still submit nothing.
